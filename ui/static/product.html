SAMPARK is not choosing the bigger payment. It compares each opportunity's expected net value against the cost of spending the one contact this customer can receive in this window: expected_net = p̂ × amount − channel cost − expected incentive − fatigue cost. The fatigue term prices what a contact costs the future — every later recovery attempt on that customer moves one step down the decay curve. With the frozen Phase 4 constants that cost is ₹541.20 per contact for a customer with nothing else open, so a failed_payment only clears the bar above about ₹1,978. A ₹1,000 failed payment is below it and is declined with allocation.negative_expected_net. That is the answer to “why not just retry everything?” — and it is arithmetic from committed, frozen constants, not a rule written for this demo. A low-value payment from a customer with several other open items scores differently again; the amount alone never decides.

Razorpay provides

  • payment infrastructure and checkout
  • orders, payment links, payment status
  • the failure event and its error code
  • webhooks
  • payment execution primitives

SAMPARK adds

  • revenue-at-risk detection and normalisation
  • cryptographic agent identity and capability scope
  • hard policy enforcement (consent, quiet hours, contact caps, interlocks)
  • expected-value scoring and allocation across competing agents
  • bounded intervention, budgeted and reversible
  • a hash-chained audit log and a deterministic explanation

SAMPARK does not replace Razorpay's payment infrastructure. It adds a decision and recovery layer around failed and recoverable payments.

Guided demo integration control

  1. 1. Open a session
    Creates a throwaway PostgreSQL schema and registers payment_retry_agent. The protected audit chain is never touched.
  2. 2. Create the ₹1,000 test payment
    Razorpay Test Mode payment link. SMS and email notifications are switched off — this demo never contacts a real person.
  3. 3. Create the contrast payment
    A second real test payment, above the allocator's break-even. Optional, but it is what makes the comparison visible: SAMPARK declines one of these and funds the other, from the same kind of failure signal.
  4. 4. Make the payments fail
    Open each link and pay with a Razorpay test card that fails. Nothing here simulates the failure — Razorpay produces it, and SAMPARK reads the real error code back. Razorpay test card reference →
  5. 5. Let SAMPARK decide
    Reads each failed payment back from Razorpay, normalises it into a risk item, and runs the unmodified mediation path: identity → scope → hard policy → score → allocate → reserve → execute.
  6. 6. Prove it
    Recomputes every hash and checks the linkage.
Failure injection: Arms the mock channel so the next send fails. The grant rolls back, the budget and contact slot are released, and no double-send occurs.
